# Pinterest

## 1. Тема и целевая аудитория
Pinterest - платформа для визуального поиска и рекомендаций, где пользователи могут сохранять картинки и идеи в подборки

### MVP
1. Регистрация/авторизация
2. Просмотр ленты рекомендаций
3. Поиск по пинам (картинки с описанием и ссылкой)
4. Сохранения пина на свою доску
5. Загрузка своего пина
6. Возможность ставить лайки и добавлять комментарии

### Ключевые особенности сервиса

1. Бесконечная лента, важна стабильная непрерывная подгрузка контента
2. Большое время жизни контента
3. Основной способ организации контента через доски

## Глобальная балансировка

### Функциональное разбиение по доменам

http://www.pinterest.com/ - основной домен сервиса

Раздача медиа/статики производится через i.pinimg.com/s.pinimg.com соответственно.

Тогда можно применить разные виды балансировки. Для основного домена: GeoDNS, для отдачи тяжелого медиа-контента: CDN и Anycast.

### Обоснование расположения датацентров

Из пункта 1, видим, что основной процент пользователей сосредоточен в США, Индии, Бразилии, России и странах Европы. Необходимо выбрать датацентры таким образом, чтобы наиболее полно покрыть эти регионы.

Предлагается следующее расположение:

- США (Вирджиния) - один из крупнейших рынков
- Западное побережье США (например, Орегон) - покрываем западную часть Северной Америки
- Европа (Франкфурт) — покрываем Европу и часть из России
- Индия (Мумбаи) — покрываем Южную Азию;
- Южная Америка (Сан-Паулу) — покрываем Латинскую Америку.

Большая часть трафика приходится на медиа-контент, который обслуживается CDN и уменьшает нагрузку на дата-центры.

### DNS-балансировка

Используется GeoDNS балансировку, при которой возвращается IP ближайшего датацентра. При этом возвращается несколько адресов и в случае недоступности одного из датацентров трафик направляется в соседний регион.

### Anycast-балансировка

Для доставки медиа будем использовать Anycast. При использовании Anycast один и тот же IP-адрес анонсируется из множества точек сети. Маршрутизация BGP автоматически направляет пользователя к ближайшему узлу CDN.

Если нужного изображения нет в кэше, CDN-узел обращается к серверу в одном из датацентров и сохраняет объект локально. Такой подход снижает задержку загрузки изображений и уменьшает нагрузку на основные датацентры.

## Локальная балансировка

После глобальной балансировки, DNS возвращает адрес ближайшего дата-центра, а если он недоступен, то возвращает IP соседнего региона.
Медиа-контент раздается через CDN с Anycast, основная часть трафика обрабатывается на CDN-узлах, а если запрашеваемого контента нет в кэше, то CDN обращается к дата-центру.

### Балансировка входящих запросов

Для основного домена используется двухуровневая балансировка: L4-балансировщики с VIP для распределения TCP между L7 узлами, и L7-узлы для SSL termination, роутинга HTTP, health check, rate limiting и failover.  
Соединения между L7 узлами распределяется через round-robin. L7-узлы для балансировки используют reverse proxy - Nginx.   
Серверы объединены через VRRP (keepalived). 

### Балансировка межсервисных запросов

Для этого используется service discovery внутри Kubernetes, балансировка осуществляется автоматически между инстансами сервиса, а при масштабировании список доступных инстансов обновляется через service discovery.

Сервис делает запрос к другому сервису, имя сервиса резолвится через CoreDNS, затем запрос идет на ClusterIP, kub-proxy распределяет трафиу между подами сервиса через round-robin.

Дополнительно можно использовать client-side retry, timeout для снижения задержек.

### Схема отказоустойчивости

На уровне дата-центров используется схема active-active, при отказе одного региона DNS перенаправляет трафик в соседний. L4 балансировщики также работают в active-active, еще используют health-check. Все L7 узлы работают в пуле, при падении одного узла трафик распределяется по оставшимся.

Также отказоустойчивость обеспечивает Kubernetes, который автоматически перезапускается при падении пода, исключает недоступные поды, использует Horizontal Pod Autoscaler при масштабировнии.

Рассчитаем количество балансировщиков. Учитываем два ограничения: пропускную способность сети и SSL termination, при расчете количества берем максимум из этих параметов. 
По данным Nginx [[14]](https://blog.nginx.org/blog/testing-the-performance-of-nginx-and-nginx-plus-web-servers) один балансировщик может 50k TLS-соединений в секунду. Для Pinterest основная нагрузка идет на API, из пунка 2, пиковая нагрузка на API = 420k RPS.  
Предположим, что у нас 70% keep-alive соединений. Тогда TLS CPS = 0.3 × 420k = 126k TLS/sec. Тогда N_ssl = 126k/50k = 3.  
Рассчитаем по ограничению сети: из пунка 2, приблизительная нагрузка на API = 10-15 Gbit/s. Если один балансировщик может принять 25 Gbit/s, то N_net = 15/25 = 1.  

Берем максимум = 3, учитываем резервирование N+1 = 4 L7 балансировщика на датацентр.  

L4 должен содержать как минимум 2 узла (active-active), берем 2.
